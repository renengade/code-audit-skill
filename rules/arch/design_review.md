# 设计与架构安全评审

## 一、信任边界

### 检查点

- 哪些接口暴露公网、哪些仅内网
- 网关/反代与应用之间是否有认证
- 服务间调用是否双向认证
- 是否盲信 `X-Forwarded-For`、`X-Real-IP`、`Host`
- 内部服务是否假设“内网可信”

### 危险信号

```python
ip = request.headers.get("X-Forwarded-For")  # 可伪造
if request.headers.get("Host") == "admin.internal":
    grant_admin()
```

### 建议

- 只信任已知代理层，使用 `ProxyFix` 并限制 hop 数
- 内网服务同样做认证与授权
- 管理面与业务面分离，独立域名/端口/网络

## 二、最小权限

| 对象 | 检查 |
|---|---|
| 数据库账号 | 是否只有所需库表的 CRUD，禁用 DDL/DROP |
| 云 AK | 是否最小策略、是否可长期有效 |
| 容器 | 是否 root、是否只读根文件系统、是否 `privileged` |
| 文件系统 | 上传目录是否可执行、是否越权可读 |
| 消息队列 | 是否可跨租户消费 |
| CI Token | 是否 `contents: write`、是否可读 secrets |

## 三、暴露面

- 调试端点：`/debug`、`/__debug__`、Django Debug Toolbar
- 文档：`/docs`、`/redoc`、`/openapi.json`
- 管理后台：`/admin`、`/actuator`
- 监控：`/metrics`、`/health` 是否泄露内部信息
- 错误页：是否返回堆栈、SQL、路径
- 目录列表：静态服务器是否开启
- 默认账号：是否仍存在

## 四、威胁建模（轻量）

对核心模块问 4 个问题：

1. 我们在保护什么？（资金、身份、数据、可用性）
2. 谁能接触它？（匿名、登录用户、管理员、内部服务）
3. 信任边界在哪？（公网/内网、租户间、服务间）
4. 最坏情况是什么？（越权、篡改、泄露、拒绝服务）

产出：资产 → 入口 → 威胁 → 控制 的简表。

## 五、多租户

- 租户 ID 是否来自会话而非请求
- 所有查询是否强制租户条件
- 缓存 Key、队列 Topic、文件路径是否带租户
- 跨租户导出/统计是否隔离
- 管理员跨租户操作是否审计

## 六、密钥与加密架构

- 密钥是否集中在 KMS/Vault，而非代码/配置
- 是否支持轮换
- 加密算法与模式是否合规（AES-GCM、RSA-OAEP）
- 传输是否强制 TLS，是否校验证书
- 敏感数据是否加密存储、是否脱敏展示
- 备份是否加密

## 七、认证与授权架构

- 认证方式（Session/JWT/OAuth2）是否统一
- Token 生命周期、刷新、撤销
- 权限模型（RBAC/ABAC）是否覆盖对象级
- 是否有集中鉴权层，避免每个接口手写
- 失败是否默认拒绝（fail-closed）

## 八、日志与可追溯

- 登录、权限变更、资金操作、数据导出是否审计
- 日志是否集中、不可篡改、有保留期
- 日志是否含敏感信息
- 是否有告警规则

## 九、依赖与发布架构

- 是否有 SBOM、锁文件、哈希校验
- 构建产物是否签名
- 发布权限是否分离
- 回滚方案是否可用
